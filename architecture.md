# PMJAY Claim Pre-Authorization Prediction API Architecture

## 1. System Overview
The PMJAY API is a robust, AI-powered backend system built to automate the processing, validation, and scoring of medical pre-authorizations and claims. It leverages FastAPI for routing, PostgreSQL for data persistence, and a multi-agent orchestration pipeline that integrates with LLMs (Claude, GPT-4o, Gemini) to analyze submitted documents, validate medical compliance, and assign a final verdict (PASS, REVIEW, FAIL).

**Tech Stack:**
- **Framework:** FastAPI (Python)
- **Database:** PostgreSQL (with `asyncpg` and SQLAlchemy/Alembic for migrations)
- **Validation & Serialization:** Pydantic
- **AI Integration:** Multi-provider abstraction layer (Anthropic, OpenAI, Google)

## 3. Core Components

### 3.1. API Routing Layer (`backend/routes/`)
The application defines several isolated routers handling specific domains of the system:
- **`auth.py`**: User authentication, Login logic, and JWT token generation using `passlib`.
- **`admin.py`**: Administrative controls (configuring package fields, updating agent prompts, and editing dynamic scoring weights).
- **`patients.py`**: CRUD operations and search endpoints for PMJAY patients. 
- **`packages.py`**: Provides the `/form-schema` endpoint, which the frontend uses to dynamically generate claim upload forms based on DB config.
- **`claims.py`**: Handles:
  1. `POST /` - Accepts patient and document payloads, stores them in the DB.
  2. `GET /{id}/preflight` - Internal checks to ensure mandatory docs are uploaded before wasting AI resources.
  3. `POST /{id}/score` - Triggers the `ClaimOrchestratorAgent`.
  4. `POST /extract-fields` - Utility endpoint to extract text fields from multi-modal PDFs directly using AI.

### 3.2. Data Models and Schemas (`backend/models/schemas.py`)
The system strictly relies on **Pydantic schemas** for API input/output validation. Key schemas include:
- `PackageFormSchema`: Describes the dynamic form fields required for a specific medical package.
- `ClaimSubmitRequest` & `PreauthSubmitRequest`: Payload structures encompassing patient details, hospital ID, and arrays of `ClaimDocumentInput` (text + base64 files).
- `ClaimScoreReport`: The ultimate output of the AI pipeline, containing verdicts, total weighted scores, hard block reasons, and actionable recommendations.
- `AgentResult`: The raw analysis structure generated by individual AI agents.

### 3.3. AI Client Abstraction (`backend/core/ai_clients.py`)
To prevent vendor lock-in, the system uses an `AIClient` abstraction supporting multi-modal (vision+text) operations:
- **`ClaudeClient`**: Interacts with Anthropic's Claude API, natively utilizing the Anthropic Files API for robustly processing clinical PDFs.
- **`OpenAIClient`**: Interacts with GPT-4o using base64 image structures.
- **`GeminiClient`**: Connects to Google's Gemini models, effectively utilizing the Gemini File API for large files over the inline threshold.
- **`StubClient`**: Provides mocked responses without external calls for rapid local testing.

## 4. Deep Dive: The `ClaimOrchestratorAgent` and Multi-Agent Execution

The brain of the system resides in `backend/agents/orchestrator.py` via the `ClaimOrchestratorAgent`. Rather than having a monolithic script evaluate a claim, the Orchestrator coordinates multiple micro-agents, injects database-driven contexts, and computes a final verdict. 

### 4.1. Orchestrator Initialization and Context Gathering
Before the Orchestrator runs, the `/score` route (in `claims.py`) prepares a massive `claim_context` dictionary. **Nothing is hard-coded at the Orchestrator level; everything is injected from the DB.** 

The context includes:
- **Standard Metadata**: `patient_name`, `dob`, `admission_date`, `discharge_date`, etc.
- **`required_fields`**: Pulled from `package_documents`.
- **`package_rate_inr`**: Financial cap pulled from the `packages` table.
- **Dynamic Relevance Groups**: The backend queries `text_field_groups` joined with `package_documents` to find exactly which document group belongs to which category. It creates arrays like `clinical_relevant_groups`, `lab_relevant_groups`, `identity_relevant_groups`, etc. 
- **Dynamic Prompts**: A mapping of `{agent_name: system_prompt}` pulled from the `agent_prompts` database table.

### 4.2. Orchestrator Execution Flow
The orchestrator executes agents in a strict two-step asynchronous flow:

**Step 1: The Extraction Bottleneck (Synchronous)**
The orchestrator isolates the `DocumentExtractorAgent` and runs it first.
- **Purpose**: To convert messy PDFs, base64 images, and raw text into clean, structured JSON data. 
- **Why First?**: The output of this agent (`context["DocumentExtractorAgent"]`) provides structured ICD-10 codes, patient names found in documents, dates, and extracted numerical data. This shared memory is passed to all subsequent agents so they do not have to re-parse the documents.

**Step 2: Concurrent Validation (Asynchronous `asyncio.gather`)**
Once the shared context is populated, the Orchestrator runs all validation agents simultaneously. Each agent accesses the shared `claim_context` (from the DB) and the parsed `context` (from the Extractor).

### 4.3. How Agents Utilize Dynamic Values
Each agent in `backend/agents/agents.py` follows a similar pattern to leverage dynamic database configuration:

1. **Filtering Relevant Documents via DB Groups:**
   Agents do not assume a document named "blood_test" is a lab report. They look at `claim.get("lab_relevant_groups")`. For example, `LabAnalyzerAgent` does:
   ```python
   lab_groups = claim.get("lab_relevant_groups", [])
   lab_docs = _docs_by_relevant_groups(documents, lab_groups)
   ```
   If an administrator marked a custom group (e.g., "hematology_records") as `lab_relevant = true` in the DB, the agent automatically includes it.

2. **Fetching Dynamic Prompts:**
   Agents *have* hard-coded default prompts defined as fallback strings in the code. However, they ALWAYS attempt to fetch the dynamic prompt injected by the DB first.
   ```python
   # Fallback hard-coded prompt
   default_prompt = "You are a lab analyzer... {patient_name}" 
   
   # Attempt to fetch DB prompt
   template = claim.get("agent_prompts", {}).get(self.name)
   if template:
       try:
           ai_prompt = template.format(...) # Interpolate variables
       except Exception:
           ai_prompt = default_prompt # Fallback if formatting fails
   else:
       ai_prompt = default_prompt
   ```
   This means **each and every agent supports dynamic prompting**. An administrator can modify the prompt instructing the `ClinicalRelevanceAgent` on how to judge an ICD-10 code directly via the Admin API, and the pipeline will use the new instructions immediately on the next run.

### 4.4. Overview of the Agents

- **`DocumentExtractorAgent`**: Converts raw files into JSON data.
- **`IdentityValidatorAgent`**: Verifies patient identity across documents defined in `identity_relevant_groups`. It uses strict fuzzy-matching rules in its prompt to handle name reversals ("Kumar Rajesh" vs "Rajesh Kumar") but flags completely mismatched identities.
- **`PackageComplianceAgent`**: A **pure rule-based agent (no AI call)**. It strictly compares the uploaded document keys against the `required_fields` injected from the DB. 
- **`ClinicalRelevanceAgent`**: Evaluates documents from `clinical_relevant_groups`. It cross-references the patient's condition against the claimed package, verifying that the diagnosis logically supports the procedure and that extracted ICD-10 codes match.
- **`LabAnalyzerAgent`**: Analyzes documents from `lab_relevant_groups`. Its prompt asks the LLM to flag 'H' (High) or 'L' (Low) abnormal values and ensure test dates fall within the admission timeline.
- **`RadiologyValidatorAgent`**: Parses radiology reports, ensuring the clinical imaging aligns with the package intent.
- **`BillingAnalyserAgent` (Claim Only)**: Evaluates invoices. It references the `package_rate_inr` dynamically fetched from the DB to ensure billed amounts do not exceed state package limits.
- **`DischargeSummaryAnalyserAgent` & `ICPAgent` (Claim Only)**: Analyze hospital stay notes.

### 4.5. Dynamic Scoring and the Verdict Engine
After `asyncio.gather` resolves, the Orchestrator receives an `AgentResult` (Score 0-100, Passed boolean, and Flags) from every agent.

**1. Dynamic Weights:**
The Orchestrator fetches `weights` specific to the submitted package (e.g., Cataract Surgery might weigh Radiology at 0%, but Knee Replacement weighs it at 30%). It computes a weighted average: `weighted = result.score * weight`.

**2. Hard Block Processing:**
The Orchestrator manually checks for critical failure flags. If an agent returned a severe violation, it triggers a "Hard Block":
- `IdentityValidatorAgent` returned `hard_block = True`.
- `PackageComplianceAgent` reports >2 missing mandatory documents.
- `RadiologyValidatorAgent` detects dates outside the admission period.
- `BillingAnalyserAgent` detects billing above limits.

**3. Final Verdict Calculation**:
- `FAIL`: If a Hard Block was triggered OR the `total_weighted_score` is below the system's `REVIEW_THRESHOLD`.
- `REVIEW`: If the score is between the `REVIEW_THRESHOLD` (e.g., 60.0) and `PASS_THRESHOLD`. Requires human audit.
- `PASS`: If the score exceeds the `PASS_THRESHOLD` (e.g., 85.0) and has no hard blocks. Automated approval.

## 5. End-to-End System Flow

The complete lifecycle of a claim or pre-auth submission through the architecture follows these distinct phases:

### Phase 1: Ingestion (`POST /api/v1/claims/`)
1. **Submission:** The frontend sends a JSON/multipart payload including `patient_id`, `package_code`, metadata, and base64 encoded or raw text documents.
2. **Validation:** The `claims.py` router validates the `patient_id` and `package_code` against the database.
3. **Storage:** The system generates a `claim_ref` and saves the master record to the `claims` table. All associated files are persisted to the `claim_documents` table. A response with the new `claim_id` is returned.

### Phase 2: Pre-flight Verification (`GET /api/v1/claims/{id}/preflight`)
1. **Configuration Lookup:** The API looks up the dynamic `required_fields` configuration for the submitted `package_code` from the `package_documents` table.
2. **Document Check:** It compares the documents saved in the DB against the mandatory package requirements.
3. **Readiness Status:** It returns a status (`ready=True/False`) informing the client if the claim is structurally complete enough to send to the AI engine.

### Phase 3: AI Scoring Orchestration (`POST /api/v1/claims/{id}/score`)
1. **Internal Guard:** The `/score` endpoint calls the pre-flight check internally. If missing mandatory docs, it immediately aborts (HTTP 422).
2. **Context Assembly:** The system queries the DB to construct the `claim_context` (dynamic prompts, scoring weights, document group configurations, and financial limits).
3. **Execution Initialization:** The `ClaimOrchestratorAgent` is instantiated with the configured `AIClient` (e.g., Claude or Gemini).
4. **Step 1 - Data Extraction:** The orchestrator runs `DocumentExtractorAgent`. PDFs and images are sent to the AI to be structured into JSON (extracting text, ICD-10 codes, names).
5. **Step 2 - Concurrent Validation:** Using `asyncio.gather`, the orchestrator dispatches the structured data to all relevant micro-agents simultaneously (e.g., `IdentityValidatorAgent`, `LabAnalyzerAgent`, `BillingAnalyserAgent`). Each agent applies its specific rules and dynamic DB-injected prompts.
6. **Step 3 - Consolidation:** Agents return their individual `AgentResult` objects (0-100 scores, boolean pass/fail, and flags).

### Phase 4: Final Verdict & Persistence
1. **Weighted Calculation:** The orchestrator multiplies each agent's score by its dynamic package weight to compute the `total_weighted_score`.
2. **Hard-block Evaluation:** Severe flags (e.g., mismatched identity, billed amount > cap) immediately override the score and trigger a `FAIL` verdict with a `hard_block_reason`.
3. **Thresholding:** If no hard blocks are present, the score is compared against `PASS_THRESHOLD` and `REVIEW_THRESHOLD` to determine the final `Verdict` (PASS, REVIEW, FAIL).
4. **Database Commit:** The complete, detailed report is saved to the `claim_score_reports` table as JSON-structured rows. The original claim status is updated to `SCORED`.
5. **Response:** The system returns the `ClaimScoreReport` to the client frontend for display, including flags, scores, and AI recommendations.
